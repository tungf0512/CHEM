# iOS macOS Lockfile Reproducibility

## Problem

An iOS React Native repository can pass JavaScript checks while its macOS native
build is not reproducible. A lockfile generated by an older Ruby/Bundler pair may
cause Bundler to restart into an incompatible version, and CocoaPods can fail while
parsing an Xcode project before compilation starts. Letting every CI run regenerate
locks hides both classes of drift.

## Context / Trigger Conditions

- `Gemfile.lock` has a `RUBY VERSION` or `BUNDLED WITH` entry that does not match
  the Ruby/Bundler selected by `ruby/setup-ruby`.
- Bundler installs one version and then re-executes the version recorded in the
  lockfile, producing runtime errors such as `DidYouMean::SPELL_CHECKERS` under a
  newer Ruby.
- `pod install` fails through Nanaimo with an error like:
  `Dictionary missing ';' after key-value pair for "CURRENT_PROJECT_VERSION",
  found "("`.
- CocoaPods resolves successfully but rewrites tracked Xcode project or plist
  files, causing a lock-refresh commit to contain unrelated product changes.

## Solution

1. Choose one supported macOS toolchain and use it everywhere. In CHEM this is the
   Ruby patch in `mobile/.ruby-version`, Bundler `2.7.2`, CocoaPods `1.15.2`, and
   the checked-in Node version. Pin the same Bundler explicitly in CI rather than
   relying on the lockfile's executable to auto-restart.
2. Generate `Gemfile.lock` and `ios/Podfile.lock` only on a macOS runner using a
   manual `workflow_dispatch` refresh. Run Codegen first when the Podfile depends
   on generated React Native artifacts.
3. If Nanaimo reports a missing semicolon at a `$(...)` token, inspect the exact
   Xcode project setting. Quote variable-valued settings, for example:

   ```text
   CURRENT_PROJECT_VERSION = "$(CHEM_BUILD_NUMBER)";
   PRODUCT_BUNDLE_IDENTIFIER = "$(CHEM_BUNDLE_ID)";
   ```

   This preserves Xcode substitution while producing valid input for the
   xcodeproj/Nanaimo parser.
4. Treat the generated locks as source-controlled artifacts. Normal foundation and
   release CI should use frozen Bundler installation and `pod install`, then fail
   if either lockfile changes (`git diff --exit-code`). Do not silently regenerate
   locks during verification.
5. Before committing a refresh, snapshot or restore product source files that
   CocoaPods is allowed to rewrite. Scope the commit to exactly `Gemfile.lock` and
   `Podfile.lock`; never commit `Pods/`, generated Codegen output, or unrelated
   Xcode/Info.plist changes.

## Verification

- The refresh job completes on macOS and both lockfiles are non-empty.
- A clean checkout installs with the pinned Bundler in frozen mode and `pod install`
  exits successfully without changing either committed lock.
- `xcodebuild -list` sees the workspace/scheme, the iOS Simulator Debug build
  compiles, and native Swift tests pass.
- In CHEM, the real refresh completed in run `36323536247` and the final frozen
  foundation build completed successfully in run `36374844760`.

## Example

```sh
cd mobile
BUNDLE_FROZEN=true bundle _2.7.2_ install --jobs 4 --retry 3
BUNDLE_FROZEN=true bundle _2.7.2_ exec pod install --project-directory=ios
git diff --exit-code -- Gemfile.lock ios/Podfile.lock
```

Use the refresh workflow to change the locks; use the commands above only to verify
the committed resolution.

## Notes

- `Podfile.lock` should be committed even when the `Pods/` directory is ignored;
  it is the reproducible dependency resolution, not a generated cache.
- A successful dependency refresh does not prove device behavior or Apple signing.
  Keep physical-device validation and signing credentials as separate gates.
- Do not solve a parser error by disabling CocoaPods, weakening frozen checks, or
  hand-editing lockfile metadata.
