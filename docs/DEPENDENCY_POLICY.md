# Dependency and generated-artifact policy

- `mobile/package-lock.json` is committed and `npm ci` is the JavaScript install path. Node is pinned by `mobile/.nvmrc` (`20.19.6`).
- iOS tooling uses the exact Ruby in `mobile/.ruby-version` (`3.4.11`). `mobile/Gemfile` reads that file directly so the Bundler Ruby requirement cannot drift from the setup-ruby input.
- Bundler is explicitly selected as `2.7.2` in the macOS workflows. Normal foundation and signed-release CI use frozen installs and fail if either committed lockfile drifts. Intentional refreshes run `ios-lockfile-refresh.yml`, which regenerates metadata through Bundler/CocoaPods on macOS and commits only the two lockfiles. Lock metadata must be generated by the toolchain, never hand-edited.
- CocoaPods is pinned to `1.15.2`, the version already present in the foundation lock, with the existing Xcode project parser constraints retained. This task stabilizes the toolchain rather than combining a CocoaPods/Xcode project-parser upgrade with the first native build.
- `mobile/ios/Pods/` and `mobile/build/` are generated and ignored; never commit them.
- React Native Codegen artifacts under `mobile/build/generated/` are generated during CI/build and are not committed.
- `mobile/ios/Podfile.lock` is source-controlled policy. The manual macOS refresh workflow creates it through a real `pod install`, validates scope, and commits it. Do not fabricate or hand-edit the CocoaPods resolution. Foundation CI uploads a diagnostic copy, but it is not the source of truth once the lockfile commit exists.

The historical Linux lockfile was generated on Ruby `3.0.2p107` with Bundler `2.2.22`; that metadata was incompatible with the pinned macOS Ruby `3.4.11`. The canonical refresh must therefore be produced by Bundler `2.7.2` on macOS and then committed. The original CI artifact endpoint required repository admin access, so the refresh workflow is the reproducible fallback when artifact download is unavailable.
